## Scope resolved before implementation

Use a fixed SHA256 digest of the previously verified owner's canonical Supabase UUID in server code. It is a feature filter, not a credential or permission. Compare only the trusted userId already supplied by authenticated routes or the existing scheduled token-owner iteration. No model/request-selected rollout owner, env setting, new registry or new account flag. All other users use the exact existing legacy payload and one-upsert path.

Minimal read-only code evidence: app/api/whoop/sync-all/route.ts selects whoop_tokens.user_id with no activity predicate and invokes incrementalSync for each row. Therefore inactivity does not exclude an account that remains connected. vercel.json declares daily 10:30 UTC. No inactive account/token/health records were queried; actual retained connections and scheduler execution remain unverified. Do not disable, delete, inspect or alter those accounts or change this job.

## Exact additive schema

On public.whoop_recovery, public.whoop_sleep and public.whoop_cycles add nullable columns with no defaults: provider_created_at timestamptz(6), provider_updated_at timestamptz(6), provider_interval_start timestamptz(6), provider_interval_end timestamptz(6), timing_ingested_at timestamptz(6), provider_timezone_offset text, provider_score_state text, timing_mapping_version text, timing_provenance jsonb. Add provider_sleep_id text on recovery and provider_cycle_id text on sleep. Existing hosted provider-ID columns are text; incoming numeric cycle IDs must be positive safe integers before canonical decimal text conversion, and UUID links remain validated UUID strings.

No old-column changes, NOT NULL, defaults, indexes, data UPDATE/DELETE, triggers, functions, grants, RLS changes, extensions or new tables. Existing rows receive null new fields from DDL without rewriting/relabeling old values. Shared DDL still requires ACCESS EXCLUSIVE locks: use a 2-second lock timeout and 10-second statement timeout in one transaction, abort rather than wait/retry automatically. No guarantee of zero downtime/cost; production lock duration and relation sizes remain unmeasured. Existing SELECT-star APIs may show additional null keys for non-owner rows.

## Exact future mapping and ordinary re-ingestion

Keep every existing transform, health score/calculation and extractDateFromTimestamp behavior unchanged, including the legacy fallback date. Never expose that date as verified measurement day. Do not add a derived event-date/local-date column in this increment.

A complete timing snapshot requires explicit-offset calendar-valid lifecycle timestamps with at most six fractional digits, updated_at >= created_at, neither after the supplied ingestion instant. Sleep requires an ordered closed interval and valid provider fixed offset; cycle allows a null open end. Intervals must not end/start in the future. Recovery retains its exact cycle/sleep identities and direct lifecycle fields only; its interval/offset stay null, with no guessed date/nearest-record join or additional provider request. Retain only documented score states SCORED/PENDING_SCORE/UNSCORABLE. Reject malformed/unknown timing from the metadata projection without changing the legacy health write.

Reject ISO year zero because PostgreSQL timestamptz cannot represent it. Before grouping, duplicate conflict identities use the exact legacy single-bulk path, preserving its atomic rejection instead of silently turning duplicates into separate successful health writes. No deduplication, new lookup or partial duplicate save is introduced.

For the owner only, partition each existing domain's records into two homogeneous payload groups: legacy-only records and records with complete timing snapshots. This avoids mixed JSON-column unions nulling retained timing. Missing/malformed/incomplete timing uses the legacy-only group, preserving any older timing fields. A later valid payload for an existing provider ID replaces that row's timing snapshot with the exact newly returned source metadata; this is ordinary re-ingestion, not retrospective reconstruction. No wider lookback, manual fetch, saved historical payload replay or backfill. Original legacy fields continue their existing provider-upsert behavior. No timing revision history is claimed.

timing_ingested_at is the application timestamp submitted with a valid timing snapshot and committed only if that row upsert succeeds. It is not the SQL commit instant, every health-row ingestion, provider creation, source capture or observation time. This replaces the earlier proposed last_record_ingested_at name to avoid claiming a marker for legacy-only writes. An empty result changes no timing; existing batch status/count semantics stay unchanged. At most one additional database upsert per mixed owner/domain batch (three extra per sync); non-owner query count/payloads remain unchanged. No added SELECT, RPC, provider request, retry or model call. Partial failures retain existing retry/idempotency expectations and do not constitute an atomic whole-batch transaction.

Offsets preserve only the provider's supplied fixed offset for its interval. timestamptz preserves instants at six-digit precision, normalizing offsets to UTC; the separate offset column preserves the provider label. No IANA zone, historical DST transition or midnight observation is inferred. The current PR97 read/eligibility helper remains unchanged and will not automatically promote retained timing to readiness.
