# Socius durable context and chosen LLM transition

## Goal

Make Socius the durable, model-independent home for an athlete's fitness context and validated records, while the athlete's chosen LLM provides the single input/output interface and creates programming and synthesis. A fresh conversation should recover the necessary facts from Socius, explain what is current or uncertain, and continue useful coaching without copying context between chats or requiring an embedded API-model coach.

Socius owns durable storage, provenance/history, deterministic calculations and validated operations. The chosen LLM owns exercise/program selection, programming reasoning, interpretation and conversation. Historical Socius-generated plans remain readable; future LLM-authored plans become durable only through explicitly authorized validation and acceptance. The current embedded authoring paths are legacy behavior to retire safely, not a foundation to expand.

This is an ordered delivery plan, not authorization for its future deployments, database migrations, data writes, settings, credentials or schedules. Work starts with the existing owner pilot. General multi-user security and least-privilege delegated credentials are not established.

## Product acceptance

1. **Fresh conversation.** In a newly started conversation in an approved harness, the user asks what to train today without pasting old chats. The chosen LLM retrieves current goals, requirements, constraints, equipment, training days, reviewed playbook, user-approved plan/rationale, recent actual work, relevant metrics/assessments, nutrition and recovery. Every domain reports its time window, source dates, provenance and populated/missing/stale/unavailable/truncated coverage. Empty records never establish that no exercise or meals occurred.
2. **Programming authority.** The chosen LLM returns a specific proposed session and rationale grounded in those facts. It follows an applicable current user-approved plan unless evidence justifies proposing a change, makes unsaved proposals explicit, and does not silently activate a replacement. Socius does not call a mandatory hidden model or generate the programming. Deterministic estimates remain labelled and traceable; uncertain or unrevalidated numeric targets stay explicit.
3. **Durable continuity.** Authorized saves and corrections survive a fresh conversation and an approved harness change. Records retain source identity, capture/event times, estimate/confirmation status and revision history. User-approved plans retain authorship, rationale and the exact context/reference versions used. Earlier plans, prescriptions and completion links remain interpretable.
4. **Logging in one user plane.** Workout photos/screenshots can be interpreted in the selected harness, reviewed and saved with receipts. Later, explicitly authorized nutrition photo ingestion creates an estimated log automatically, with optional refinement instead of a mandatory second coach chat. Duplicate delivery does not create duplicate records; a correction preserves what changed and why. An optional daily nutrition review requires separate scheduling approval.
5. **Bounded operations.** Read tools use the authenticated owner and grant no write authority. Each later write is a narrow validated operation with expected version, idempotency, an outcome receipt and uncertain-save reconciliation. Cross-owner, malformed and stale requests fail closed. No broad SQL, arbitrary host-tool dispatcher or service-role fallback becomes the user interface.
6. **Evidence before completion.** Software work is done after decisive tests/review pass and the scoped change is committed and merged through normal CI and branch protection. Deployment, actual owner-data/harness verification and product acceptance are separate states and may remain pending. Passing tests demonstrates software behavior, not improved athletic outcomes.

Greg's pilot remains APEX-focused, five training days weekly, with purposeful isometrics in warm-up or accessories supporting each training day's stimulus. Priorities among explosive power, strength and strength endurance should follow the largest meaningful gap against confirmed goals. These are user requirements, not a general APEX-specific foundation. Exact numerical targets/thresholds and their current durable-record completion remain unverified.

## Completion and commit discipline

Record these independently for each slice: scoped/approved work; code prepared; commit hash; tests and independent review where risk requires; PR/CI/merged hash; release authorization; deployed version; actual owner-data/harness result; product acceptance or exact blocker. The software definition of done is tests/review passed, committed and merged. Deployment and real-data acceptance remain separately evidenced. A commit is not a release, a200 response is not proof of useful content, and a populated table is not complete context coverage.

Use one logical commit per finished change where safe, with relevant tests and evidence. Audit index and dirty files before staging; use explicit file allowlists; preserve unrelated changes. If a historical boundary is not recoverable, report it instead of inventing a clean past.
