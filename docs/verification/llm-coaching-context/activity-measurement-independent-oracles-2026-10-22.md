# Fitness-Tracker-txs independent acceptance oracle

Assessment base: `666ab8daf084cc3eff3260f8db1226f0725021cb`.
Scope: one pre-candidate, source-based oracle design; no candidate named `activity-measurement*` inspected, no repository edits, no credentials or database execution, no production access. This is an acceptance specification, not evidence that a future candidate passes. The delegated requirement is authoritative.

## Verified base evidence

- `app/lib/coach/activity-record-contract.ts:28,34,46,98`: existing closed schema requires set UUIDs, offers whole-block amendment, and omits retained block fields such as `time_cap_s`, `score_model`, `block_score` and event `prescribed`. Thus round-tripping the actual retained shape through its create/replacement contract is not the desired fix.
- `app/lib/coach/activity-record-tools.ts:99,123,132,153,177`: provenance currently operates on broad groups; request fingerprint/recovery precedes mutable-state reads; amendment is expected-revision checked and calls the existing capture RPC. Existing metadata corrections preserve nested JSON at the TypeScript level, but normalization and persistence remain separate boundaries.
- `app/lib/capture/normalize.ts`: projections are derived from explicit represented facts; source blocks remain in the canonical record. Server metadata is filtered; no inferred quantities are intended.
- `docs/migrations/recommendations-migration.sql:484-559`, especially 536 and 543: the later replacement of the amendment engine unconditionally deletes/recreates block scores and refreshes PRs on workout amendments. Earlier definition has the same behavior at `docs/migrations/capture-receipts-migration.sql:502,509`. Changes must account for the effective later function definition.
- `capture_refresh_prs` deletes/recreates affected history and unsupported assertions. Equal displayed numeric values cannot prove identity/history preservation.
- `app/lib/coach/external-performed-work-context.ts:56`: nested set reader retains velocity but omits `vbt`. Its field validator only permits booleans for `is_pr`, so simply adding `vbt` to one allowlist is insufficient.
- `app/lib/coach/planning-history.ts`, `historyFieldProvenance`: exact source-path field lookup precedes a fallback group; there is no generic ancestor-path inheritance. Container-only provenance does not establish individual velocity leaf provenance.
- Existing `test/coach/activity-record-tools.test.ts` uses generated UUID `set_details` and full-block correction. Its notes/readiness tests compare source blocks but do not establish unchanged projection row IDs/history. Existing concurrency test uses independent native PostgreSQL backends and observes a lock wait; PGlite sequential tests alone cannot establish cross-backend race behavior.
- ADR-0044 preserves the unsupported wrapper/untyped-record boundary and rejects incomplete numeric meal macros. Neither boundary should be silently widened.

## Synthetic fixture and comparison oracle

Seed a local isolated canonical workout using existing fixture mechanisms, not the typed create API that rejects its retained shape. Use synthetic owner/request/entity UUIDs and quantities. It has exactly three blocks, in order CARDIO, CARDIO, STRENGTH. Each has retained `block_type`, `title`, `time_cap_s`, `score_model`, `block_score`, and `segments`; each event has `movement_name`, `performed`, and `prescribed`. Third block first event contains eight ID-less `performed.sets` entries, each with explicit load/reps; zero-based index 3 also has `vbt:true`, and none has velocity. Use e.g. synthetic load values 31,34,37,40,43,46,49,52 kg and reps 2,3,4,5,6,7,8,9. Include duplicate movement names in another event to defeat name matching. Keep unknown retained metadata and nulls in multiple untouched branches.

Repeat the core case with `performed.set_details`, including an existing UUID where present and a separate ID-less legacy variant. Preserve array spelling and absent IDs; never migrate `sets` to `set_details`, add IDs, reconcile repetitions, infer velocity, or select by name.

Snapshot canonical record JSON, all provenance, revision/event precision, mutation receipts, `block_scores`, `personal_records`, `benchmark_prs`, accepted program/session/check-in/observation links, and historical source revisions before each operation. For retained JSON use deep structural equality with exact scalar types/null-vs-absence/array order, not object-key order. For database identity compare complete rows ordered by stable ID, including ID and creation timestamps, across the relevant owner's affected history and unrelated control rows.

## Required acceptance cases

1. **Revision-bound narrow success.** Owner reads revision R. Typed patch identifies the existing set solely by block/segment/event/array/index path bound to R, and adds a supplied velocity object such as value 0.47, unit m/s, metric mean_concentric, synthetic device, valid synthetic timestamp. Only the explicitly supplied measurement leaves and their exact provenance change. Every other JSON subtree, all eight sets, the fourth set's load/reps/vbt, block metadata, prescribed work, notes, and all preexisting IDs remain equal. Same entity ID, revision R+1, exactly one new mutation/receipt and source revision. No set ID is fabricated.
2. **Second array and repeat names.** Same result for `set_details`. A repeated movement name elsewhere cannot redirect the patch. If IDs exist, they remain unchanged and do not expand update scope. Array/index is never interpreted as a movement search or mutable name identity.
3. **Read fidelity without authority promotion.** Reader retains boolean true and false markers as recorded, explicitly unverified VBT markers. Invalid marker types are omitted with a diagnostic. A marker alone never creates velocity or device facts, independent completion, comparability, assessment eligibility, PR claims, or numeric-policy authority. Both nested arrays retain exact paths and nullable/missing measurements. Direct owner getter retains the complete stored source JSON.
4. **Exact-leaf provenance.** Every supplied measurement leaf (value/unit/metric/device/measuredAt, including explicit nulls) has its exact canonical source path. No broad blocks/quantities upgrade, occurrence confirmation, unrelated origin change, deletion of sibling overrides, or provenance for an unmodified sibling. Existing model estimates remain estimates merely after review; an unrelated estimated load or other set must retain its original provenance and must not be erased by a new measured velocity. Missing/extra/mismatched provenance rejects rather than silently extending its scope.
5. **No projection churn.** Notes-only, readiness-only, and VBT-only updates produce source revisions/receipts, but preserve complete block-score, personal-record, benchmark-PR rows, including IDs/timestamps/previous_value/is_pr. Use nonempty seeded PR history plus an unrelated workout with the same exercise, so an illicit refresh cannot hide behind empty tables. Assert that destructive projection operations are not reached (for example fail-on-delete/update/insert triggers in disposable tests), not merely that final counts/values match.
6. **Database owns projection decision.** Direct owner calls to the persistence RPC get the same safe behavior; no client skip boolean, sentinel `p_blocks`, forged claim, or adapter-only decision can suppress required recomputation. Derive comparison inputs from locked stored state and validated new state, not caller-supplied projections. Projection equivalence includes all facts actually used by the affected helper, such as workout date/order, execution eligibility, block score/type/title/RX, performed amounts and units, and provenance that gates PR eligibility. Notes/readiness/velocity alone do not affect those facts. JSON blocks inequality alone is too broad. Projections may be compared independently: block-score equivalence does not imply PR equivalence.
7. **Positive recomputation controls.** Alter a helper-supported event-level load/reps/unit, score, date, or qualifying quantity provenance. The relevant derived facts must update; a date/order change must update previous-value history where applicable. Existing stale unsupported assertions must still invalidate on real source-fact change. A load under a nested set currently ignored by all projection helpers does not justify a new numeric policy or fabricated totals. Full-block changes continue to use validated persistence and cannot smuggle a projection skip.
8. **Conflict and path stability.** Two commands with different request UUIDs and the same expected R race: exactly one commits R+1; loser gets conflict with no source/projection mutation. A prior reorder or unrelated revision change makes an old path stale even if its named movement/value still looks familiar. Stale revision never rebinds a path automatically. Test the database compare under locking, beyond the adapter pre-read check.
9. **Replay and response loss.** Same request UUID/action/target/revision/path/measurement/provenance replays the original saved receipt and immutable revision, even after later corrections or array reordering. Changed path/value/unit/provenance/action with the same key rejects. Canonical object key order is replay-equivalent; array order matters. Lose transport after mutation commit and after finalization: status resolves original receipt, exact retry makes no extra revision, projection row or measurement. Receipt absence remains explicitly unresolved; never issue a fresh replacement key automatically.
10. **Authentication and rollout.** Existing request-local verified owner/client/issuer/audience/active-grant checks and DB subject agreement stay required before queries/writes. Other owners, revoked/wrong grants, anonymous users and principal/DB mismatch cannot read or amend the target or discover another owner's receipts. Default-off MCP write gating covers the patch operation; getters remain read-only. No new scopes, credential requests, table grants, executable internal-function grants, or activation.
11. **Strict malformed/units/path rejection.** Reject negative/fractional/out-of-bounds indices, missing blocks/segments/events/array, scalar `sets`, nonobject selected set, missing/null revision, zero/unsafe revision, unsupported roots/array names/leaf keys, whole-array or prototype keys, identity/score/prescribed mutations, and mixed incompatible patch/replacement forms. Reject malformed velocity shape, numeric strings/NaN/Infinity/out-of-range values, unknown unit/metric, invalid date/time/offset, raw media, oversized values, unknown input properties, empty patches and duplicate/conflicting paths. Do not coerce, convert units silently, interpret arbitrary JSON paths, create missing target sets, or partially apply a multi-leaf patch. Null/delete semantics must be explicit and tested rather than conflated with absence.
12. **Rollback and linked execution.** Inject snapshot/receipt failure after canonical update in a disposable transaction: canonical JSON, revision, projections, receipts, and linked accepted prescription/check-in/observation state all remain unchanged. Same original request can recover/retry according to actual outcome. Supported completed program execution uses the dedicated authority path and retains original links/history; accepted prescriptions are never rewritten. Existing wrapper/untyped records still return explicit unsupported conflict with zero canonical amendment. Missing meal macros still reject with no canonical meal and never become zeros.

## Qualification limits

This design independently identifies expected behavior before candidate review. No candidate tests were run or assessed and no production runtime behavior is claimed. A release claim needs the exact candidate hash, real local PostgreSQL persistence/rollback evidence and independent-backend race evidence where concurrency is claimed. Prepared SQL must remain unapplied remotely under the delegated scope. Any runtime migration/deployment/flag activation is outside this assessment.
