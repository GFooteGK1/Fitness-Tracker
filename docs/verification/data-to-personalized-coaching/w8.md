## Delivered behavior

`app/components/NextActionCard.tsx` presents the same persisted recommendation on Today and Coach. The default is one action, a factual rationale and a canonical destination. Plan and Log remain available during loading, disabled capability, pending work, source outage and expiry. Evidence, explicit meal-logging coverage and recent outcomes use optional disclosures. Nutrition copy retains logged-only, estimate and coverage limits. Invalidated observed outcomes become unknown in the current view while preserving their earlier factual payload in details.

Shown acknowledgements require viewport intersection and visible document state. The persisted request identity survives remounts. Done remains a report and never writes a meal or workout. Not applicable, a visibly confirmed defer deadline and an adjustment request use separate idempotent response events. Adjust exposes the canonical destination after confirmation. Lost responses remain recoverable even after the original card is suppressed or expires. Only the backend's explicit `noWriteConfirmed` and `refreshRequired` proof releases a stale event identity for a fresh review; unknown transport and payload conflicts retain it.

The client uses an owner-keyed component, authenticated mutation checks, local-day/timezone scope and expiry. A confirmed source save schedules a bounded independent refresh. A refresh begun before that save is rejected; concurrent save notifications coalesce into a trailing refresh. Recommendation computation failure cannot change the capture result. Partial bundles with a confirmed child also trigger refresh, while their unresolved children keep advice hidden.

Origins enter the initial text, photo, template, reviewed-food, Coach, queued-photo and program-completion request. Frozen request bodies preserve them through retries. The legacy session writer omits the new origin field when feedback v2 is unavailable. Program completion uses the frozen correction/retry helper, so its pending body can be recovered after a reload. Draft commits retain server-staged origins. Canonical correction/delete, baseline confirmation, intent confirmation, target changes and accepted plan changes also prompt an independent refresh.

## Capture uncertainty and review repairs

`app/lib/client/capture-uncertainty.ts` separates replay identity from confirmation proof. Advice is withheld while an owned request may have committed but has not been reconciled, including before-commit transport loss. Unattempted queued photos do not claim canonical data or block publication. Attempted queue items and unavailable queue proof remain guarded. Retained confirmed receipts no longer block advice.

Durable recovery records bind the owner, surface and original request ID. Another tab's confirmed request on the same surface cannot clear an unknown request. Creates retain the server request identity without raw text or photo bytes; corrections retain their frozen normalized request. Reopening a tab restores recoverable identities, including multiple requests on one endpoint. Alternate corrections use their original endpoint, method, body and request identity. Photo bytes remain only in the account-owned IndexedDB queue until confirmation. Confirming one request clears only its matching uncertainty proof.

Independent review also resolved duplicate initial loads, date-only source labels shifting to the prior day, incomplete source labels, invisible shown acknowledgements, missing Adjust navigation, raw JSON in default evidence, and response recovery after a card disappears. A broader test run exposed an unstable `CaptureRecovery` effect dependency when an auth wrapper returns a fresh object; the effect now depends on the scalar owner ID.
