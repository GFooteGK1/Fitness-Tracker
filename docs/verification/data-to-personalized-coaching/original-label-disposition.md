## What the existing decision gate actually requires

The existing measurement-need path is `evaluateAdaptation` → `nextMeasurement` → weekly `buildSignalRequest`; there is no general production gate that accepts the fixture boolean `collectionChangesDecision` as evidence.

1. [Evaluation boundary](../../../app/lib/coach/adaptation-evaluator.ts#L188): the evaluator needs an authoritative adaptation-review context, matching goal and active plan, available storage, complete evidence selection, a valid as-of time, a plan hypothesis for that goal and its evaluation policy. [Boundary validation](../../../app/lib/coach/adaptation-evaluator.ts#L438) checks those conditions. Incomplete structural input returns a hold with **no named next measurement**, rather than inventing the missing requirement; see [reviewWithoutSnapshot](../../../app/lib/coach/adaptation-evaluator.ts#L804).
2. [Requirement selection](../../../app/lib/coach/adaptation-evaluator.ts#L464): the hypothesis selects its metric, semantic role and assessment definition, expected signal, requirement window and compatible series. [Sample summarization](../../../app/lib/coach/adaptation-evaluator.ts#L580) uses dated exposures and freshness. Missing, stale or insufficient series determine the first unmet requirement at [lines 247–253](../../../app/lib/coach/adaptation-evaluator.ts#L247). The returned [nextMeasurement](../../../app/lib/coach/adaptation-evaluator.ts#L387) comes from that requirement, not from a UI value being absent.
3. [Weekly signal request](../../../app/lib/coach/weekly-review.ts#L613): the weekly review resolves the named assessment and finds a compatible exercise/assignment before producing a metric/protocol request. The [hold mapping](../../../app/lib/coach/weekly-review.ts#L492) can instead retain a collect/hold state with no signal request when placement is unavailable or an exact outcome protocol is required. A general collect/hold state therefore does not prove a specific optional-RPE or exact-repetition solicitation.
4. [Targeted outcome review](../../../app/lib/coach/targeted-review.ts#L59) additionally requires an installed direct metric/assessment/protocol adapter and the exact outcome binding. [Sample matching](../../../app/lib/coach/targeted-review.ts#L30) distinguishes movement, variation, equipment, distance, repetitions/load/duration and modifiers. A catalog family match alone does not authorize a new numerical policy.
5. The current recommendation rules can navigate an [existing authoritative collect-signal review](../../../app/lib/recommendations/rules.ts#L46) or request a [defined supported missing baseline](../../../app/lib/recommendations/rules.ts#L53). The original four cases supply neither that persisted review nor a complete defined-baseline contract. Their `goalId` and `goalConfirmed` fields are insufficient to manufacture one.

Existing tests demonstrate that this path is real, without supplying the missing facts to the original cases after the fact: [weekly compatible measurement request](../../../test/coach/weekly-review.test.ts#L94), [declared supporting session-RPE series](../../../test/coach/weekly-review.test.ts#L575), and [direct performance versus session-RPE support](../../../test/coach/adaptation-evaluator.test.ts#L190). These fixtures contain accepted plans and declared evidence requirements. They are not evidence that one original effort value resolves an unspecified requirement.

## Effort: missing fixture context versus missing policy

An existing role for session effort **does** exist. The [resilience domain specification](../../../app/lib/coach/adaptive-plan.ts#L107) declares `session.rpe` as a `training_signal` alongside a readiness proxy. [Hypothesis construction](../../../app/lib/coach/adaptive-plan.ts#L344) specifies at least two comparable observations within its declared window. A strength review can also consume a previously declared supporting RPE requirement, as the test above demonstrates. The [session-RPE catalog](../../../app/lib/coach/adaptive-programming-contracts.ts#L468) classifies it as a training signal, not a direct strength outcome.

The two original effort pairs provide one value, a goal identifier and a provenance/scope distinction. They do not identify the accepted hypothesis, policy, assessment/protocol, comparison series, dated prior exposures, other requirements or existing review. Therefore this is primarily **missing fixture authority/context**, not proof that the product lacks all measurement-request capability. Even after its provenance is resolved, one value cannot automatically satisfy the existing two-exposure requirement; a prior compatible exposure and the rest of the gate would need to be supplied. The absent facts cannot be inferred from `collectionChangesDecision:true`.

The implemented provenance guarantees are independently defined by [stored feedback decoding and explicitness](../../../app/lib/coach/execution-feedback.ts#L134), [completion-observation provenance binding](../../../app/lib/coach/evidence-context.ts#L862), [exercise signal validation](../../../app/lib/coach/session-signals.ts#L40), and [nullable fractional session feedback](../../../app/lib/coach/execution-feedback.ts#L194). These support the predicate-only dispositions without implying solicitation, benefit, or numerical eligibility.

A future **separate, fully specified engineering scenario** may exercise the existing declared requirement without a new policy. By contrast, a rule that asks for session RPE for any goal merely because it is missing, treats a single value as sufficient, converts hardest-set effort to session effort/RIR, or uses it to select new dose is an additional policy decision. That desired behavior belongs in explicitly scoped qualified-policy work; it is not an adapter repair or authority supplied by these original labels.

The original repetition pair supplies a raw block field path and a range/exact value, with no such typed assessment, protocol, binding, hypothesis, dated comparable series or canonical correction transition. `exactQuantityRequired:true` supplies no production authority for treating those raw repetitions as fixed-load capacity. Thus the original pair is predicate-only. A generic policy deciding when an arbitrary range must be replaced by an exact value is **not implemented or licensed by these facts**. Designing it requires a declared decision use, collection burden, supported measurement protocol and qualified review where it affects numerical programming. Do not fill the range midpoint, add a hidden request threshold, or relabel ordinary workout reps as a tested assessment to force the original expected labels.

## Historical replay: complete local clarification

The [exposed source adapter](../../../test/personalized-coaching/engineering-source-adapter.ts#L60) calls this operation and checks unchanged inputs. It does not have an accepted historical decision ID to replay, and creating a new advice object would change the subject of the case.
