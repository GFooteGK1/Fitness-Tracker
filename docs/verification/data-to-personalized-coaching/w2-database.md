# W2 capture database verification

Status: implementation and focused local database verification complete; independent parent review and all adapter integration remain in progress. No provider, hosted database, credentials or production actions were used.

## Files and contract

- `supabase/migrations/20260918020000_capture_receipts.sql` and identical `docs/migrations/capture-receipts-migration.sql`.
- `test/database/capture-receipts.test.ts` executes the real logging, runner, atomic completion, W1 feedback and signal chain, plus the existing nutrition fast-logging, personal-record schema and record-idempotency migration, then applies W2 twice.
- `activity_drafts` holds normalized owned proposals, expiry, revision and terminal committed/discarded state. Expiry is checked on use; nothing silently purges drafts. Standalone edits/discards use `save_activity_draft` with request identity and expected revision. A frozen request's draft cannot be edited independently. Explicit standalone draft commit binds the original draft to a frozen child; a proposed analysis correction targets the existing entity/revision instead of creating another activity.
- `logging_request_items` freezes stable source item IDs, order, normalized payload, SHA-256 fingerprint and optional response snapshot before any child saves. A SQL-generated operation ID owns each canonical commit. Exact replay returns the same receipt after completion or canonical deletion. The existing parent ledger retains its saved entities.
- `activity_revisions` holds immutable canonical snapshots, derived block scores, provenance, event and capture timestamps, actor and operation IDs. `original_entity_id` remains after deletion; nullable composite canonical FKs detach only the canonical ID column, preserving owner. `deleted` terminal snapshots support historical replay without exposing a soft-deleted activity to old readers.
- Canonical meals/workouts have `capture_revision`, `capture_provenance`, `captured_at`, and `capture_input_method`. Legacy capture metadata remains unknown; the first legacy immutable snapshot is recorded at the actual snapshot transaction time, never backdated to creation. A new v2 snapshot preserves the operation's event time separately from capture time. Same-date workout amendments preserve that original event timestamp. `event_precision` is date or timestamp. Date-only workout receipts retain YYYY-MM-DD; the internal date encoding is not a reported midnight event. Timestamp operations validate workout local-date scope, with an explicit raw timezone offset where needed.

The public RPCs are `freeze_logging_request_items(uuid,jsonb)`, `commit_logging_request_item(uuid)`, `amend_logged_activity(text,uuid,integer,text,jsonb,jsonb,jsonb)`, `amend_program_execution(uuid,integer,text,jsonb,jsonb,jsonb)`, `delete_logged_activity(text,uuid,integer,text)`, `save_activity_draft(text,uuid,integer,jsonb,boolean)`, `commit_activity_draft(uuid,integer,uuid)` (draft ID, expected revision, parent ledger UUID), and `cancel_logging_request_item(uuid)` (child operation ID). The draft ID and expected revision are null on new draft creation. Every mutation derives owner from authentication. Amendment and draft request identities replay only exact payloads.

## Persistence and correction behavior

Meals recompute totals from supplied normalized item macros. Quantity origin and review state remain separate; correcting an estimate does not turn it into a measurement. Ordinary block projections derive only supported exact known quantities; ranges, unspecified units or unfamiliar exercise representations remain null. Model `is_pr` is discarded. Fractional session effort is preserved in the normalized immutable `reported_rpe`, with an unsupported integer projection left null. Raw media keys/data URLs and server-owned record identities/metadata are rejected; no raw image/audio persistence is added.

Program-runner corrections use only the dedicated execution amendment. The source workout keeps its prescribed-session link and accepted prescription; original check-ins and observation groups remain unchanged. The new revision records `execution_supersession` with the previous revision, prescribed session, accepted plan and prescription, and original check-in/observation IDs. Future evidence consumers must invalidate the applicability of superseded execution projections while retaining those original records for replay.

Initial athlete-reported quantitative commits and subsequent corrections replace/rebuild supported PR projections transactionally. Corrections replace block scores and recompute supported affected PR histories. `personal_records` follows the existing weight/reps/time/volume directions with explicit performed loads and units. Known benchmark `FOR_TIME` and `AMRAP` scores are rebuilt only when exact titles and scoring type identify a compatible comparison, with RX scope preserved. Unsupported or ambiguous assertions are withheld. New exact record reconstruction requires athlete-reported quantities and confirmed/corrected review; correcting model-estimated numbers does not qualify them. Prior revision snapshots retain the affected workout's old PR projections. Workout receipts expose `projectionsStatus: recomputed_supported_only`, which must not be displayed as universal PR certainty. This is deterministic factual projection, not a dose or progression policy.

Canonical UPDATE/DELETE privileges are revoked from authenticated callers so correction paths must use the audited RPCs. Existing legacy create APIs remain callable. Their private retained implementations have no external execute grants; the public wrappers prevent appending around a frozen list and prevent finishing a parent while a child remains pending. The parent stays processing on partial success, and adapters must reconcile/retry the existing child IDs before finalizing it. Explicit cancellation locks the owner, ledger, child and draft in the same order as commit; pending or expired children become terminal canceled with durable `noWriteConfirmed` proof. A committed child cannot be canceled. Cancel replay returns the same proof, and future commit of that original identity is rejected. A mixed saved/canceled request retains its receipts and cannot be called safe to duplicate wholesale. Sequential commit-first/cancel-first outcomes are tested; actual simultaneous connections are not.

All new tables have FORCE RLS and owner-only authenticated reads, with no authenticated or service-role direct writes. Public/anonymous/service-role execute grants are revoked for new functions; only public action RPCs are granted to authenticated. Internal SQL helpers remain private. Same-owner canonical, request and draft references are composite. Auth-user deletion cascades staging/audit/request state. The account test deletes canonical activity through the supported path before deleting the auth owner; it does not claim to redesign the existing account-deletion policy for unrelated canonical tables.

## Remaining verification boundary

### Manual workout observation detachment

The W6 integration verifier exposed the existing `performance_observation_groups_workout_owner_fk` preventing deletion of an observed manual workout. The W2 repair retains `original_workout_id`, a same-owner `source_workout_deletion_revision_id`, deletion time and explicit `canonical_workout_deleted` reason. Only an actual owned terminal capture revision authorizes exclusion and subsequent column-specific FK detachment. Observation metadata, measurement values and original source identity remain immutable. Ordinary source reassignment and unaudited linked deletion are rejected. Program-runner ordinary deletion stays prohibited.

The executable regression covers canonical deletion, exact receipt replay, preserved original values, exclusion, cross-owner denial and attempted source identity forgery. W6's integrated deletion test now succeeds and retains review invalidation. The full W1/W2/W6 SQL plus independent W2 API/core run passed **113 tests across seven files**; the W1/W2/W3 script passed **9 tests**.

A stronger account-deletion check exposed a separate pre-existing failure: retained observation values do not cascade from `auth.users`, so deleting the account fails `performance_observation_values_group_owner_fk`. This is tracked in **Fitness-Tracker-24x**, with exact reproduction in its description. At coordinator direction, account cascade semantics were not expanded in this repair. The earlier account-cascade test remains scoped to detached capture history without linked observation values; this slice does not claim complete account-deletion support for the pre-existing evidence schema.

### Planned session capture

The additive `record_coach_session_capture(uuid,text,jsonb,timestamptz,text,jsonb,jsonb)` accepts the same named arguments as `record_coach_session_result_v2` and returns JSON `{result, receipt}`. It requires feedback version 2 and invokes the unchanged atomic completion RPC before capturing anything. A new completed workout receives program input-method metadata, a revision-1 snapshot and an immutable receipt in the same transaction. An injected snapshot failure test verifies rollback of the workout, check-in and session terminal transition. As-prescribed blocks and quantities remain `copied_template`; modified explicit performed work is `athlete_reported`. Optional RPE and duration have separate provenance, and absent RPE stays unknown. Fractional explicit RPE remains in the snapshot's `reported_rpe` while its unsupported integer projection is null.

The mutation store key is `session-capture:<checkin UUID>`. The original completion RPC validates the complete original payload before receipt lookup, so changed replays still fail. Exact replay returns the initial receipt after later execution amendments. A key collision with an unrelated draft mutation is rejected. The receipt event is the workout date with date precision, and its capture time is actual transaction time. Skipped sessions and pre-wrapper completions return a null receipt rather than manufacturing historical snapshot coverage. The existing v1 row-returning API is unchanged. The new function is authenticated-only, with public, anonymous and service-role execution revoked.

Final combined database plus independent server regression run: **104 tests passed across six files** (the four database files above plus `test/api/capture-recovery.test.ts` and `test/capture/corrections.test.ts`). Initial wrapper test setup used an empty derived-block array for a nonempty correction; aligning it with the established normalized contract resolved the fixture error. No implementation failure remains from that check.

PGlite executes actual PostgreSQL functions, constraints and privileges but supplies a single engine; these tests do not demonstrate true simultaneous multi-connection transactions or browser reload/account transitions. Real concurrency, all-save-path route integration, stale `/api/check-prs` client payload protection, and full UI reconciliation remain parent/W9 verification responsibilities. Independent SQL review is required before W2 closure. No claim of release readiness is made by this database slice alone.
