## Findings resolved after author repair

1. **Important — confirmed outcomes can describe a different plan from executable allocations.** `app/lib/coach/planning-intent-server.ts:20` only attaches the confirmed intent; `app/lib/coach/adaptive-plan.ts:244` derives goals, scheduled assessments, expected signals and demand from legacy profile allocations, then appends `confirmedOutcomes`. A confirmed aerobic outcome plus a legacy strength setup can therefore produce a strength prescription with an aerobic confirmed-outcome marker. Two same-domain outcome measurements likewise do not alter the generic domain assessment. The existing snapshot test explicitly attaches a run goal to a different golden profile and checks only that the marker survived. Require executable domain/assessment compatibility, keep distinct outcome measurement links, and refuse or clearly disclose unsupported event coverage without implying complete event support. Author confirmed the missing adapter and is implementing bounded compatibility checks/assessment linkage.

2. **Important — scheduled baseline reuse ignores execution supersession.** `app/lib/coach/planning-intent-server.ts:45` admits a `coach_completion` group from metadata plus workout/session IDs. The SQL trigger in `docs/verification/data-to-personalized-coaching/training-intent.sql:171` repeats this check, but neither looks at the current workout capture revision. W2 execution amendment preserves the original observation group while incrementing `workouts.capture_revision`; a new intent can therefore reuse an old quantity baseline after it was corrected. Current candidate lookup and new confirmation must reject superseded sources, while old accepted intent snapshots remain intact. Add app/SQL tests using a completed then amended source. Author notified.

3. **Important — invalid saved setup can become implicitly confirmed defaults.** `app/program/rolling-program-page.tsx:673` sets a provisional true confirmation, replaces invalid/missing saved schedule values with the current draft defaults, then validates the substituted object at `:696`. A saved schedule with valid days but unsupported `sessionMinutes:20` becomes the default duration and can return `setupConfirmed:true` merely because schedule/equipment objects exist. This contradicts explicit confirmation of unknown/invalid availability. Validate saved required fields before fallback and retain `setupConfirmed:false` when any field is missing/invalid. Author notified with reproduction and regression request.
