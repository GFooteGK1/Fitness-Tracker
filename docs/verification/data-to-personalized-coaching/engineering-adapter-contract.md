# Engineering adapter fact contract

This document describes input materialization only. It contains no replacement holdout cases, labels or outputs. The outer schema remains `engineering-scenarios-v1`: flat facts, one changed fact per counterfactual, and existing three rule families. Scenario IDs, titles, expected decisions, assertion prose and forbidden prose do not enter the materializer.

## Common source facts

Identity fields are strings. `requestOwner` and `evidenceOwner` select synthetic owners; omitted owner uses the athlete identity. Evidence ownership includes plans, sessions, intent, observations and meals; saved nutrition targets remain request-owner records. `retrieval` can be `failed` or `truncated`; omission means complete. `agentOffsetMinutes` uses the agent convention. `localDate` is a valid date, `nowUtc` an ISO timestamp, and `localHour` an optional number. Defaults are local noon 2026-09-17 at UTC-5. All tests are synthetic and use no provider or hosted service. Read-based families can compose these authority/retrieval gates. `response:not_applicable|done_reported` applies existing ranker suppression in every read-based family. SQL transaction families have their own strict contracts below; additional read-family keys are not silently accepted there.

## Read-based accepted-plan family

`planId`, `planStatus`, optional `sessionId`, `sessionDate`, `sessionStatus`, `canonicalWorkoutId` materialize an existing persisted plan/session. Plan status defaults accepted; session date defaults the current local day. Proposal facts are `reviewState`, `reviewId`, `reviewBasisPlanId`. Existing pain boundary facts are `existingSafetyReview`, `painOrigin`, with no novel physiological policy. Snapshot preference/movement facts are retained in the stored accepted prescription. Response suppression uses existing `response` enum values. These facts are passed to production context readers, rules and ranker; no current plan is compiled from expected behavior.

`reviewState` is scoped by family: accepted-plan `proposal_ready` means an existing proposed adaptation; logged-nutrition values are only capture review states (`unreviewed|athlete_confirmed|corrected`). It is not a shared enum or a source of confirmation for another family.

## Defined-baseline family

Single-outcome facts: `goalId:string`, `goalConfirmed:boolean`, `protocol` or `goalProtocol`, optional `baselineStatus`, `measurementId`, `measurementProtocol`. Installed shorthand protocols are `run_5000m_track_elapsed_seconds` and `sprint_100m_electronic_seconds`; an observed `run_1609m_track_elapsed_seconds` materializes a distinct distance binding. `capability:'unsupported'` preserves explicit unsupported goal wording. Proxy provenance is separate from direct baseline linkage.

Dual-distance facts: `goalIds:string[2]`, `goalsConfirmed:boolean`, `firstGoalBaseline` and `secondGoalBaseline` each `missing|confirmed_comparable|achieved`, optional `goalPriority:string[2]` containing each ID once. `goalDistancesMeters:number[2]` supplies explicit distances; absent values use the documented 400/5000 meter standard-track scaffold. Each outcome has its own direct measurement and baseline identity. An `achieved` fact materializes the persisted goal status; the adapter does not calculate attainment from that label.

Equipment facts: `goalId`, `goalConfirmed`, `measurementId`, `requestedEquipment`, `observedEquipment`, `metric:'strength.load'`, `unit:'kg'|'lb'`, `transferPolicy:null`. Requested equipment must be supported by the existing goal schema; an unmatched observed value remains unmatched. Optional `movementId` and `repetitions` select the installed standard repetition-maximum assessment binding; defaults are barbell bench press, one repetition, standard variation. No transfer, tolerated load, or dose is inferred.

Existing weekly-review families use the invariant accepted-plan/series scaffold documented separately: goal priority (`goalIds`, `priorityConfirmed`, `firstGoalAttained`) or broad assignment mapping (`signalScope`, `signalMovement`, `assignmentMovements`, `transferMapping`). These call the real weekly-review builder; fixture conflict/collection labels never directly determine action.

No general conditional effort or exact-quantity solicitation policy exists in this input contract. `effortScope`, `requestedScope`, `value`, explicit provenance and quantity facts can exercise validators/normalizers, but require a complete installed decision gate to establish a recommendation label. Historical mode and revisions can exercise source replay; the source selector has no recommendation API result. Such predicate-only cases must not be presented as complete advice decisions.

## Logged-nutrition family

`targetConfirmed:boolean`, `targetCalories:number`, and `canonicalCalories` or `loggedCalories:number` materialize existing saved targets and canonical logged amounts. No training intent is invented. Optional `mealId` or distinct `mealIds` preserve occurrence identity; `mealRevision` is the canonical revision. `proteinLogged` is optional; required unrelated stored macro fields use explicit zero fixture values.

`origin` is a capture-origin enum; `reviewState` is a review-state enum. Copy facts are `mealOrigin:'copied_template'`, `templateCompositionOrigin` (capture-origin enum), `compositionReview` (review-state enum), and `occurrenceConfirmed:boolean`. Occurrence and composition provenance stay separate, with source-template revision references. Read-based copy cases verify provenance interpretation; actual quick-log transaction behavior is covered separately.

`coverage` is `unknown` or an explicit complete/partial-through string containing HH:MM, with optional `coverageRevision`. Read projection tests do not prove SQL coverage validity. WHOOP metadata (`whoopSyncStatus`, `coherentCompletedSnapshot`, `recoveryDate`, `strainDate`, `hrvDirection`) can exercise source eligibility independently; none is an input to nutrition arithmetic or a trend policy.

## Transaction families

Development correction and uncertain-photo families use the actual capture/recommendation SQL and actual client uncertainty gate. Fields include `currentCalculationRevision`, `mealRevision`, `photoPersistence`, `requestId`, `queuedEstimatedCalories` and canonical/target calorie values. They intentionally write synthetic canonical rows and therefore do not claim unchanged-source execution.

The SQL transaction adapters reject unlisted material fields. Provenance, owner mismatch, historical adherence/performance, wearable and copy-lineage combinations belong to the read-family adapter unless explicitly listed below; they cannot be appended to a transaction family and silently ignored. Source rows, publication/response RPCs and actual read results determine transaction decisions. Expected labels never enter these adapters.

### SQL transaction fact contract

`test/database/engineering-boundaries.ts` exports `executeEngineeringBoundaryFacts(rule, athlete, facts)`. Each invocation creates and closes an isolated database with the actual migration chain. Its result contains the visible decision, pending/ready state, canonical predicates and source-identity mapping. Symbolic fixture IDs map to owned UUIDs. SQL DATE values pass through PostgreSQL JSON serialization to match PostgREST `YYYY-MM-DD`. This is a transport adaptation, not a rule change.

All revision values are nonnegative integers. Common accepted-plan premises are `planId:string`, `planStatus:'accepted'`, `sessionStatus:'planned'` except the separate hidden-follow-up family. The accepted prescription is inserted immutably; no runtime update of its contents is used to arrange a case.

* Lease takeover: `workerLeaseToken:string`, `currentLeaseToken:string`, `sourceRevision`, `workerSourceRevision`, `responseRevision`, `workerResponseRevision`. Token strings are symbolic identities; equal labels select the same current lease. The fixture expires an actual first lease, claims its replacement, and passes the selected token and supplied worker revisions into the actual publication RPC.
* Racing response: `leaseMatches:true`, `workerResponseRevision`, `currentResponseRevision` exactly one greater, `workerSourceRevision`, `sourceRevision` at least the worker revision and at most twenty greater. One actual owner dismissal increments response revision. Explicit saved-target writes supply source increments. Readback must equal the stated current revisions; unchanged and changed source cases retain the response fence.
* Runtime scope: `capturedCapabilitiesVersion:string`, `currentCapabilitiesVersion:string`, `sourceRevision` equal to `workerSourceRevision`, `recommendationsEnabled:true`. The two runtime identities are hashed, a real candidate is published under the captured identity, and the actual SQL read uses the current one without a source write. False/absent recommendations-enabled premises are outside this isolated runtime-fingerprint family.
* Superseded follow-up: `decisionId:string`, `lifecycle:'superseded'`, `followUpDue:true`, `outcomeObservationId:string`, `outcomeComparable:boolean`, `canonicalOriginDecisionId` equal to `decisionId`, `overlappingActionIds:string[1]` containing a distinct action identity. An actual accepted-session completion carries the original recommendation origin. An actual execution amendment supplies the noncomparable variant. Publication of a second accepted-session action supersedes the first; the actual outcome evaluator and RPC process its due follow-up. The result decision addresses visibility of the original decision; the newer current action remains separately visible. Production outcome attribution limits, not fixture prose, establish overlap and no-causation language.

Nutrition transaction premises require `targetId:string`, `targetConfirmed:true`, nonnegative `targetCalories`, and `coverage:'unknown'` unless the correction family below explicitly supplies bounded coverage.

* Frozen occurrences: `authorizedChildIds:string[]` with one to twenty unique nonempty IDs, `canonicalChildIds:string[]` a unique subset, nonnegative `childCalories` and `otherCalories`, `samePayload:true`. A normalized identical meal operation is frozen per authorized occurrence. Only the stated canonical subset commits. Reconciliation retains the pending children; bundle retry bypasses already committed operations. Actual rule arithmetic reads only the canonical rows.
* Local day: `decisionLocalDate` and `currentLocalDate` are ISO dates with an integer nonnegative day difference, nonnegative `loggedCalories`, and `sourceRevision` equal to `decisionSourceRevision`. The day difference is mapped to the actual database day. A real published decision is aged by that interval as fixture clock staging, then the actual read evaluates current local-day validity and unchanged source revision. Its validity never extends past local midnight.
* Development correction: `targetId`, `targetConfirmed:true`, `targetCalories`, `loggedCalories`, `mealRevision`, `coverageRevision`, `coverage`, `currentCalculationRevision`. Initial coverage and calculation revisions must match. The fixture creates the stated original canonical calculation and performs audited amendments up to the stated meal revision. Bounded coverage wall time is mapped to a valid raw timezone on the actual database day. Additional provenance/history/copy facts are unsupported in this family.
* Uncertain photo: `targetId`, `targetConfirmed:true`, `targetCalories`, `canonicalCalories`, `queuedEstimatedCalories`, `photoPersistence:'queued'|'save_unconfirmed'`, `coverage:'unknown'`, `requestId:string`. Queued data remains outside canonical rows. Unconfirmed execution exercises both pre-commit and committed-response-loss transport branches, reads the original ledger, and retries only its frozen child. The actual request-bound client certainty gate withholds local publication until the original request is confirmed. Canonical fixture provenance is athlete-reported; the photo estimate stays model-estimated. Arbitrary origin/copy-lineage combinations are outside this family.

Initial source/response counters represent fixture prehistory. Elapsed lease/deadline/day values are test-only clock staging; actual claims, responses, source mutations, capture replays, publication, reads and outcome writes execute their production functions. SQL boundary families were verified locally before this contract was handed to the independent replacement-set author. The coordinator owns the final frozen adapter/artifact identity and any unseen-set acceptance claim.
